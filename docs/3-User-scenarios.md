## 1. 개요

**문서 목적**: 이 문서는 도메인 정의서와 PRD가 정의한 유스케이스(UC1-UC9)와 성공 기준(SC1-SC4)이 실제로 어떤 사용자 흐름 속에서 발생하는지를 구체적인 스토리 형태로 보여준다. 요구사항 목록만으로는 드러나지 않는 실사용 맥락 — 팀장과 팀원이 어떤 상황에서 어떤 화면과 행동을 거쳐 목표를 달성하는지 — 을 제공하여, 이후 기능 설계·화면 설계 단계에서 참조할 수 있는 사용 맥락 근거를 남기는 것이 목적이다.

**참고 문서**
- [1-domain-definition.md](./1-domain-definition.md) (v1.4) — 도메인 용어, 액터/권한 SSOT, 팀 라이프사이클, UC1-UC9, 성공 기준 SC1-SC4, 추적 매트릭스
- [2-PRD.md](./2-PRD.md) (v1.0) — 페르소나, MoSCoW 우선순위, MVP 범위(UC1-UC8 + 팀 라이프사이클 = Must, UC9 = Should), 오픈 이슈

**등장 인물 (일관 사용)**

이 문서의 모든 시나리오는 아래 세 명의 가상 인물을 반복 사용하여 스토리 연속성을 유지한다.

| 이름 | 역할 | 비고 |
|---|---|---|
| 지훈 | 팀장 | 팀을 최초로 생성하여 팀장이 됨 (도메인 정의서 5장) |
| 서연 | 팀원 | 지훈이 초대하여 팀에 합류 |
| 민준 | 팀원 | 지훈이 초대하여 팀에 합류 |

**범위 안내**: 본 문서의 시나리오는 화면 UI 스펙(버튼 위치, 색상 등)이나 API/데이터 모델을 다루지 않는다. 또한 PRD 8장 "오픈 이슈"에서 미정의로 남긴 세부 사항(재요청-이전요청 연결 방식, 팀원 탈퇴 시 참여자 처리, 팀장 위임 수락 절차, 충돌 감지의 팀 간 범위, 참여자 자격 범위)에 대해서는 임의로 답을 지어내지 않으며, 시나리오가 해당 지점에 닿을 경우 "(오픈 이슈: PRD 8장 참조)"로 표시한다.

## 3. 개별 시나리오

### US-01. 팀 생성 및 팀원 초대/가입

**등장 인물**: 팀장 지훈, 팀원 서연, 팀원 민준

**사전 조건**: 지훈, 서연, 민준은 각자 Team CalTalk 계정으로 로그인할 수 있는 상태이며, 아직 같은 팀에 속해 있지 않다.

**시나리오 흐름**
1. 지훈이 로그인한 뒤 새로운 팀 "디자인팀"을 생성한다. 팀을 최초로 생성했으므로 지훈은 자동으로 해당 팀의 팀장 역할을 부여받는다.
2. 지훈이 팀 관리 화면에서 서연과 민준을 팀원으로 초대한다.
3. 서연이 로그인하여 초대를 확인하고 팀에 가입한다. 가입과 동시에 서연은 해당 팀의 팀원 역할을 부여받는다.
4. 민준도 동일한 절차로 로그인 후 팀에 가입하여 팀원이 된다.
5. 지훈이 팀 구성원 목록을 열어 서연과 민준이 팀원으로 등재되어 있는 것을 확인한다.
6. 이 시점에서 "디자인팀"은 팀장 1명(지훈)과 팀원 2명(서연, 민준)으로 구성되며, 아직 등록된 일정은 없다.

**관련 UC/SC**: UC1 (로그인/인증), 팀 라이프사이클(도메인 정의서 5장 — 팀 생성, 팀원 초대/가입)

**완료 조건 / 기대 결과**: "디자인팀"이 생성되고, 지훈은 팀장, 서연과 민준은 팀원 역할로 소속이 확정된다. 이후의 모든 시나리오는 이 팀 구성을 전제로 진행된다.

---

### US-02. 팀장의 일정 등록과 팀 전체 공유

**등장 인물**: 팀장 지훈, 팀원 서연, 팀원 민준

**사전 조건**: US-01이 완료되어 "디자인팀"에 지훈(팀장), 서연·민준(팀원)이 소속되어 있다. 아직 등록된 일정은 없다.

**시나리오 흐름**
1. 지훈이 팀 캘린더의 주간 뷰를 연다.
2. 지훈이 새 일정 "주간 정기 회의"를 생성한다. 제목, 시작/종료 일시, 참여자(서연, 민준 포함)를 입력하고 저장한다.
3. 저장 즉시 "주간 정기 회의"가 팀 캘린더에 반영된다.
4. 서연이 로그인 후 캘린더를 열람하면, 별도의 전달 없이도 새로 등록된 일정이 캘린더에 표시되어 있는 것을 확인한다.
5. 민준도 자신의 캘린더 뷰에서 동일한 일정을 확인한다.
6. 서연과 민준은 해당 일정을 조회할 수 있지만, 일정을 직접 수정하거나 삭제하는 동작은 제공되지 않는다 — 두 사람 모두 팀 일정에 대해 읽기 권한만 가진다.

**관련 UC/SC**: UC2 (팀 일정 조회), UC3 (팀장의 일정 등록/수정/삭제), UC4 (일정 공유) / SC1, SC3

**완료 조건 / 기대 결과**: "주간 정기 회의" 일정이 팀 캘린더에 등록되어 팀장과 모든 팀원에게 조회 가능한 상태가 된다. 팀원에게는 쓰기 동작이 제공되지 않아, 일정에 대한 쓰기 권한이 팀장에게만 있음이 확인된다.

---

### US-03. 캘린더-채팅 연동을 통한 실시간 일정 조율

**등장 인물**: 팀원 서연, 팀장 지훈, 팀원 민준

**사전 조건**: US-02에서 등록된 "주간 정기 회의" 일정이 존재하며 서연, 민준이 참여자로 등록되어 있다.

**시나리오 흐름**
1. 서연이 캘린더에서 "주간 정기 회의" 일정을 클릭해 상세 화면을 연다.
2. 일정 상세와 함께 해당 일정에 종속된 채팅창이 나란히 표시된다.
3. 서연이 채팅에 "오후에 다른 미팅이 있어 30분 정도 늦을 수도 있을 것 같습니다"라는 메시지를 남긴다.
4. 지훈이 같은 일정의 채팅을 열어 메시지를 확인하고 "네, 늦으셔도 괜찮습니다"라고 답한다.
5. 민준도 같은 채팅에 들어와 자신이 참여하지 못했던 대화 내용을 처음부터 모두 확인한다.
6. 이 대화는 정식 변경 요청이 아닌 조율용 채팅이므로, 일정 자체(시작/종료 일시)는 변경되지 않는다.

**관련 UC/SC**: UC2 (팀 일정 조회), UC5 (캘린더-채팅 연동 조율), UC8 (일정별 채팅 이력 확인) / SC1, SC2

**완료 조건 / 기대 결과**: 캘린더와 채팅을 오가지 않고 한 화면에서 조율이 이루어지며, 대화 내용은 해당 일정에 종속되어 순서대로 보존되어 이후에도 누구나 다시 확인할 수 있다.

---

### US-04. 팀원의 변경 요청과 팀장의 승인

**등장 인물**: 팀원 서연, 팀장 지훈

**사전 조건**: "주간 정기 회의" 일정이 존재하며 서연이 참여자로 등록되어 있다.

**시나리오 흐름**
1. 서연에게 개인 사정이 생겨 "주간 정기 회의"의 시간을 변경할 필요가 생긴다.
2. 서연이 해당 일정의 채팅에서 희망 시간과 사유를 담아 변경 요청을 보낸다.
3. 지훈이 채팅에서 변경 요청을 확인하고 내용을 검토한다.
4. 지훈이 요청을 승인한다. 승인과 동시에 일정의 시작/종료 일시가 요청된 내용으로 갱신된다.
5. 지훈이 채팅을 통해 승인 사실을 서연에게 알린다.
6. 서연과 민준이 이후 캘린더를 다시 조회하면, 변경된 시간이 반영되어 표시된다.

**관련 UC/SC**: UC6 (일정 변경 요청), UC7 (변경 요청 승인/거절 — 승인 경로) / SC3

**완료 조건 / 기대 결과**: 팀장의 명시적 승인이 있은 후에만 일정이 갱신되며, 승인 전까지 원래 일정 정보가 유지되었음이 흐름상 확인된다. 변경 과정 전체가 해당 일정의 채팅에 남는다.

---

### US-05. 팀원의 변경 요청 거절과 재요청

**등장 인물**: 팀원 민준, 팀장 지훈

**사전 조건**: 별도로 등록된 "프로젝트 리뷰" 일정이 존재하며 민준이 참여자로 등록되어 있다.

**시나리오 흐름**
1. 민준이 "프로젝트 리뷰" 일정의 채팅에서 시간 변경을 요청한다.
2. 지훈이 요청을 검토한 결과 다른 참여자의 일정과 맞지 않는다고 판단하여 요청을 거절한다. 거절 사유는 채팅을 통해 민준에게 통지된다.
3. 민준이 채팅에서 거절 사유를 확인한다.
4. 민준이 대안 시간을 제안하며 다시 변경을 요청한다(재요청). 이 재요청이 이전 요청과 채팅 화면에서 어떻게 연결되어 표시되는지는 (오픈 이슈: PRD 8장 참조).
5. 지훈이 새 요청을 검토하여 이번에는 승인한다. 일정이 새 시간으로 갱신된다.
6. 해당 일정의 채팅에는 최초 요청, 거절 사유, 재요청, 최종 승인에 이르는 논의 흐름 전체가 순서대로 남아 이후에도 조회할 수 있다.

**관련 UC/SC**: UC6 (일정 변경 요청), UC7 (변경 요청 승인/거절 — 거절 및 재요청 경로), UC8 (채팅 이력 확인) / SC2, SC3

**완료 조건 / 기대 결과**: 최초 요청은 거절되어 원래 일정이 그대로 유지되었고, 재요청이 승인되어 최종적으로 일정이 갱신된다. 거절부터 재요청, 승인까지의 전체 대화가 유실 없이 보존된다.

### US-06. 일정 생성 시 충돌 경고

**등장 인물**: 팀장 지훈, 팀원 서연

**사전 조건**: 서연이 이미 참여자로 등록되어 있는 "고객사 미팅" 일정(화요일 14:00-15:00)이 캘린더에 존재한다.

**시나리오 흐름**
1. 지훈이 새 일정 "내부 워크숍"을 생성하며 참여자로 서연을 포함시키고, 시간을 같은 화요일 14:30-15:30로 설정한다.
2. 지훈이 저장을 시도한다.
3. 시스템은 서연이 참여자로 등록된 기존 "고객사 미팅"과 시간이 겹치는 것을 감지하여, 저장 시점에 일정 충돌 경고를 표시한다.
4. 경고는 참고 정보일 뿐이므로, 지훈이 원한다면 경고를 확인한 뒤에도 그대로 저장을 진행할 수 있다.
5. 지훈은 경고를 보고 실제로 시간을 조정하기로 결정하여, "내부 워크숍" 시간을 15:30-16:30로 수정한 뒤 다시 저장한다.
6. 이번에는 시간이 겹치지 않으므로 경고 없이 저장이 완료된다.

**관련 UC/SC**: UC9 (일정 충돌 감지/경고) / SC4

**완료 조건 / 기대 결과**: 참여자 시간대가 겹치는 저장 시도 시점에 경고가 표시되었고, 경고가 저장 자체를 차단하지는 않았다. 지훈은 경고를 참고하여 최종적으로 충돌 없는 시간으로 일정을 저장했다.

### US-07. 미인증 접근 차단과 팀원의 읽기 전용 권한

**등장 인물**: 미인증 사용자, 팀원 서연

**사전 조건**: "디자인팀"과 지훈이 등록한 일정들이 존재한다.

**시나리오 흐름**
1. 로그인하지 않은 사용자가 Team CalTalk에 접속을 시도한다.
2. 시스템은 해당 사용자가 인증되지 않은 상태임을 확인하고, 캘린더·채팅 등 어떤 기능도 제공하지 않은 채 로그인을 요구한다.
3. 서연이 정상적으로 로그인하여 팀 캘린더에 접근한다.
4. 서연이 지훈이 등록한 일정을 조회할 수 있지만, 해당 일정을 직접 수정하거나 삭제하는 동작은 제공되지 않는다.
5. 서연은 일정 변경이 필요할 경우, 채팅을 통한 변경 요청 경로만 이용할 수 있음을 확인한다.

**관련 UC/SC**: UC1 (로그인/인증), UC2 (팀 일정 조회) / SC3의 전제(권한 무결성)

**완료 조건 / 기대 결과**: 미인증 사용자는 어떤 기능에도 접근하지 못했고, 인증된 팀원은 일정 조회만 가능하며 일정에 대한 쓰기는 변경 요청-승인 경로로만 제한됨이 확인된다.

### US-08. 과거 일정 채팅 이력을 통한 의사결정 맥락 확인

**등장 인물**: 팀원 민준, 팀장 지훈

**사전 조건**: 두 달 전 진행되었던 "1분기 킥오프" 일정과 그에 종속된 채팅 이력이 팀에 남아 있다.

**시나리오 흐름**
1. 이번 분기 회의를 준비하던 민준이 지난 분기에 일정이 왜 그렇게 정해졌는지 다시 확인하고 싶어진다.
2. 민준이 캘린더를 지난 분기 시점으로 이동해 "1분기 킥오프" 일정을 조회한다. 기간 제한 없이 과거 일정도 캘린더에 그대로 남아 있음을 확인한다.
3. 민준이 해당 일정을 클릭해 채팅 이력을 연다.
4. 몇 달 전 오갔던 논의와, 당시 있었던 변경 요청 및 지훈의 승인 과정이 순서대로 그대로 남아 있는 것을 확인한다.
5. 민준은 이를 통해 당시 일정이 그렇게 결정된 배경을 이해하고, 이번 분기 회의 준비에 참고한다.

**관련 UC/SC**: UC2 (팀 일정 조회), UC8 (일정별 채팅 이력 확인) / SC1, SC2

**완료 조건 / 기대 결과**: 기간 제한 없이 과거 일정과 그에 종속된 채팅 이력이 유실 없이 순서대로 보존되어 있으며, 팀원이 이를 통해 과거 의사결정 맥락을 스스로 파악할 수 있다.
