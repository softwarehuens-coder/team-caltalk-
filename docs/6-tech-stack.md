## 1. 선정 기준

기술 스택 관련 논의에서 일반적으로 거론되는 기준(성능, 커뮤니티 규모 등)이 아니라, PRD와 도메인 정의서에서 실제로 도출되는 기준만 사용한다.

| 기준 | 근거 |
|---|---|
| **실시간 채팅(WebSocket) 지원** | PRD UC5("캘린더와 해당 일정의 채팅창을 함께 보면서 조율")·6장 비기능요구사항, 도메인 정의서 UC5. 저지연 양방향 메시지 전달이 필요하다. |
| **관계형 구조와 참조 무결성** | 도메인 정의서 6장 — 팀 1:N 일정, 일정 1:1 채팅, 일정 1:N 변경요청, 사용자 1:N 팀 소속. 엔티티 간 관계가 이미 명확하게 고정되어 있고 임의로 스키마가 흔들릴 여지가 없다. |
| **SC3(권한 무결성)이 요구하는 트랜잭션 일관성** | PRD SC3 — "미승인 상태로 일정에 반영된 변경 건수 0건". 변경요청 승인 시점에만 일정이 갱신되어야 하므로, "변경요청 상태를 APPROVED로 바꾸는 것"과 "일정 데이터를 갱신하는 것"이 원자적으로 함께 성공/실패해야 한다. |
| **채팅 이력의 무기한 누적에 따른 확장성** | PRD 8장 "기술적 확장성 리스크" — SC2에 따라 채팅 이력이 팀 해체 전까지 기간 제한 없이 영구 보존되므로 저장소가 선형으로 증가한다. |
| **MVP 범위의 개발 속도** | PRD 5장 — Must 항목(UC1-UC8, 팀 라이프사이클)이 MVP 범위이며, UC9(일정 충돌 감지)는 Should로 후속 배치 가능. 최소 범위를 빠르게 구현할 수 있는 스택이 필요하다. |
| **프론트/백엔드 언어 통일 필요성** | 도메인 용어(팀/일정/채팅/변경요청)가 4-project-structure.md 3.2에서 코드 전반의 고정 영문 용어로 지정되어 있다. 프런트엔드-백엔드가 같은 언어(TypeScript)를 쓰면 이 도메인 타입을 양쪽에서 재정의하지 않고 공유할 수 있어, "여러 곳에 규칙/타입이 복제되지 않아야 한다"는 4-project-structure.md 1.2 원칙을 코드 수준까지 확장할 수 있다. |
| **동시 편집 잠금 불필요(설계 단순화 여지)** | PRD 6장 — 팀당 팀장 1명 구조로 동시 쓰기 충돌이 구조적으로 발생하지 않는다. 따라서 DB 선택 시 복잡한 분산 락/낙관적 동시성 제어 기능을 우선순위에 둘 필요가 없다. |
| **(참고, Should) 시간대 중첩 조회** | PRD UC9/SC4 — 일정 충돌 감지는 MVP 이후 배치 가능한 Should 항목이지만, "동일 팀원의 겹치는 시간대 조회"라는 쿼리 패턴이 조만간 필요해질 것이 이미 PRD에 명시되어 있으므로 DB 선택 시 참고 요소로만 고려한다(필수 기준은 아님). |

## 2. 프런트엔드 스택 — React + TypeScript

프런트엔드 프레임워크 자체(React 18 vs Next.js 등)의 비교는 이 문서의 범위가 아니다. 여기서는 "React + TypeScript"라는 기확정 선택이 이 프로젝트의 요구사항과 왜 맞는지만 근거를 정리한다.

- **역할별 뷰 분기(팀장/팀원)**: 도메인 정의서 4장 권한 표에 따라 팀장은 일정 생성/수정/삭제 UI(`ScheduleForm.tsx`)를 보고, 팀원은 조회 전용 뷰와 변경요청 UI(`ChangeRequestForm.tsx`)를 본다(4-project-structure.md 6.1). React의 컴포넌트 조합 모델은 "같은 캘린더 화면에서 역할에 따라 다른 컨트롤을 조건부로 렌더링"하는 요구를 자연스럽게 표현한다.
- **캘린더 + 채팅의 동시 상태 관리(UC5)**: 월/주/일 캘린더 뷰와 일정별 채팅창을 나란히 두고 상호작용해야 한다(UC5). React 훅 기반 상태/구독 모델(`use-schedule-conflicts.ts`, `use-chat-socket.ts`)은 "캘린더에서 일정을 선택 → 해당 일정의 채팅 이력/실시간 메시지를 구독"하는 화면 간 상태 연동을 컴포넌트 트리 안에서 명시적으로 관리할 수 있게 한다.
- **TypeScript를 통한 권한 분기의 컴파일 타임 방어**: 실제 권한 판단은 서버 도메인 계층(`permission.policy.ts`)이 유일한 SSOT이지만(4-project-structure.md 2.4), 프런트엔드가 "팀장 전용 컴포넌트에 팀원 데이터가 잘못 전달되는" 류의 실수를 TypeScript 타입(`role: 'LEADER' | 'MEMBER'`)으로 미리 차단할 수 있다. 이는 SC3(권한 무결성)를 서버가 최종 보장하되, 클라이언트 단에서도 방어선을 하나 더 두는 것이다.
- **UC9(충돌 경고) 같은 부가 기능의 점진적 추가**: `ScheduleConflictBanner.tsx`처럼 독립된 컴포넌트로 분리되어 있어(4-project-structure.md 6.1), Should 항목인 UC9를 MVP 이후에 추가해도 기존 화면 구조를 재작업할 필요가 없다(4-project-structure.md 1.6 "작은 반전성" 원칙과 부합).

## 3. 백엔드 스택 — Node.js + TypeScript

### 3.1 런타임/언어 선택 근거

- **REST + WebSocket을 하나의 런타임에서 처리**: PRD Must 항목인 팀/일정 CRUD(REST 적합)와 UC5의 실시간 채팅(WebSocket 적합)이 공존해야 한다. Node.js의 이벤트 루프 모델은 다수의 유휴 WebSocket 연결(채팅창을 열어두고 대기하는 사용자들)을 적은 자원으로 유지하는 데 적합하며, 별도 런타임을 두지 않고 REST 라우트와 WebSocket 게이트웨이를 같은 프로세스 안에서 분리 운영할 수 있다(4-project-structure.md 6.2의 `chat.routes.ts` / `chat.gateway.ts` 분리 구조와 부합).
- **프런트엔드와의 도메인 타입 공유**: `Team`, `Schedule`, `ChatMessage`, `ChangeRequest` 같은 도메인 타입(4-project-structure.md 3.2 용어표)을 프런트/백엔드가 각자 다시 정의하면, 도메인 정의서가 바뀔 때 두 곳을 따로 갱신해야 하고 드리프트가 발생한다. 백엔드도 TypeScript이면 이 타입을 공유 패키지/모듈로 두고 양쪽에서 import하는 것이 가능해져, "규칙이 여러 곳에 복제되지 않아야 한다"(4-project-structure.md 1.2)는 원칙을 타입 수준까지 확장할 수 있다. 이는 선정 기준의 "프론트/백엔드 언어 통일 필요성"을 직접 충족한다.
- **MVP 개발 속도**: PRD 5장의 MVP 범위(UC1-UC8 + 팀 라이프사이클)는 CRUD + 인증 + 실시간 메시징 중심으로, Node.js/TypeScript 생태계에서 검증된 패턴으로 빠르게 구현 가능한 범위다.

### 3.2 웹 프레임워크 비교

4-project-structure.md 2장이 이미 프레젠테이션/애플리케이션/도메인/인프라 4계층을 **컨벤션으로** 확정했으므로, 프레임워크 자체가 계층 구조를 강제해줄 필요는 없다. 이 전제 위에서 최소 2개 대안을 비교한다.

| 항목 | Express | Fastify | NestJS |
|---|---|---|---|
| 구조 강제 정도 | 없음(자유도 높음) | 없음(자유도 높음, 스키마 기반 검증 내장) | 강함(모듈/DI/데코레이터로 계층을 프레임워크가 강제) |
| TypeScript 친화도 | 커뮤니티 타입 정의로 지원(`@types/express`) | 1급 시민으로 설계, 타입 추론 우수 | 1급 시민, TS 전제 설계 |
| WebSocket 통합 | 별도 라이브러리(`ws`, `socket.io`)를 직접 배선, 4-project-structure.md 구조와 자연스럽게 결합 | 별도 라이브러리 필요(Express와 유사) | `@nestjs/websockets` 등 자체 추상화 제공 — 그러나 이미 정의된 `chat.gateway.ts` 구조와 별도로 NestJS식 게이트웨이 개념을 새로 학습해야 함 |
| 학습 곡선/러닝 커브 | 낮음 | 낮음~중간 | 높음(모듈, 프로바이더, 데코레이터, DI 컨테이너 개념 필요) |
| MVP 적합성(5장 Must 범위 기준) | 높음 — 최소 구성으로 바로 라우트/미들웨어 작성 가능 | 높음 — 성능/스키마 검증 이점이 있으나 MVP에서 필수 요구사항은 아님(PRD에 처리량 NFR 없음) | 낮음 — 4-project-structure.md가 이미 계층을 컨벤션으로 정의했으므로 프레임워크 레벨의 DI/모듈 강제는 중복 투자이며, 과설계(over-engineering) 위험 |

**선택: Express.** 근거:
1. 4-project-structure.md의 4계층 구조는 이미 폴더 컨벤션으로 확정되어 있어, 프레임워크가 별도로 계층을 강제할 필요가 없다. NestJS의 모듈/DI 강제는 이 프로젝트 규모(MVP, Must 범위)에 비해 과설계이며, PRD 어디에도 이를 정당화할 요구사항(대규모 팀 협업, 복잡한 의존성 그래프 등)이 없다.
2. PRD에 명시된 비기능요구사항(6장)에는 처리량/응답시간에 대한 정량적 NFR이 없으므로, Fastify의 성능 이점은 이 시점에는 결정적 차별화 요소가 아니다.
3. Express는 가장 널리 쓰이는 Node.js 웹 프레임워크로 학습 자료·미들웨어 생태계가 가장 풍부해 "MVP 범위의 개발 속도" 기준을 가장 잘 만족시키며, `ws`/`socket.io` 같은 WebSocket 라이브러리와의 배선도 4-project-structure.md가 이미 그려둔 `presentation/websocket/` 구조에 그대로 얹을 수 있다.
4. Fastify는 유효한 차선책으로 남겨둔다(추후 처리량 요구가 명시적으로 생기면 재검토 가능).

## 4. 데이터베이스 — 실제 비교·결정

4-project-structure.md와 5-arch-diagram.md는 PostgreSQL을 "작업 가정"으로만 걸어두었을 뿐 실제 비교 분석은 수행하지 않았다. 아래는 이번에 처음 수행하는 비교 분석이다.

### 4.1 후보

실무에서 실제로 고려할 만한 3개 후보로 좁힌다: **PostgreSQL**, **MySQL**(관계형 대안), **MongoDB**(문서형 대안).

### 4.2 비교표

| 평가 기준 | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| **(a) 관계형 구조·참조 무결성**<br>(도메인 6장: 팀1:N일정, 일정1:1채팅, 일정1:N변경요청) | 강함 — FK 제약, `ON DELETE CASCADE`로 "팀 해체 시 일정·채팅 이력 함께 삭제"(도메인 5장) 규칙을 스키마 수준에서 강제 가능 | 강함 — InnoDB 기준 FK/CASCADE 동일하게 지원 | 약함 — 네이티브 FK 없음. 팀-일정-채팅-변경요청처럼 참조가 촘촘한 구조는 애플리케이션 코드에서 참조 무결성을 직접 관리해야 하며, 도메인이 이미 고정한 관계를 DB가 보장해주지 못함 |
| **(b) SC3 트랜잭션 일관성**<br>(승인 시에만 일정 반영) | 강함 — 단일 DB 내 ACID 트랜잭션으로 "ChangeRequest 상태 변경 + Schedule 갱신"을 원자적으로 처리 | 강함 — InnoDB ACID 트랜잭션 동일 지원 | 보통 — 멀티 도큐먼트 트랜잭션(4.0+)이 있으나, 문서 간 트랜잭션은 관계형 DB만큼 자연스럽지 않고 스키마가 관계형으로 설계된 이 도메인에서는 오히려 관계형 DB 대비 이점이 없음 |
| **(c) 채팅 대량 누적 대응력**<br>(PRD 8장 확장성 리스크) | 강함 — 네이티브 선언적 파티셔닝(예: 생성일자 기준 RANGE 파티션)으로 오래된 메시지를 별도 파티션으로 분리해 조회 성능을 유지하며, 추후 콜드 스토리지 이관 전략과도 자연스럽게 연결 | 보통 — 파티셔닝을 지원하나 PostgreSQL 대비 세부 제어(부분 인덱스, 파티션별 제약 등)가 제한적 | 강함(수평 샤딩 관점) — 대량 문서 저장/샤딩에 강하지만, 이 프로젝트는 채팅만 대량이고 나머지(팀/일정/변경요청)는 관계형 구조가 필요해 저장소를 이원화하는 비용이 발생 |
| **(d) MVP 개발 생산성** | 높음 — Prisma/TypeORM 등 TypeScript ORM 생태계 성숙, 마이그레이션 도구 안정적 | 높음 — 동일 수준의 ORM 지원 | 보통 — Mongoose 등으로 빠르게 시작할 수 있으나, 관계형으로 이미 고정된 도메인 모델(6장)을 문서형으로 재해석하는 설계 비용이 추가로 발생 |

### 4.3 결정: PostgreSQL

**최종 선택: PostgreSQL.**

근거:
1. 도메인 정의서 6장이 팀/일정/채팅/변경요청 간의 관계를 이미 명확한 관계형 구조(1:N, 1:1)로 확정해 두었다. 이 구조를 그대로 반영할 때 참조 무결성(FK, CASCADE)을 DB가 보장해주는 관계형 DB(PostgreSQL, MySQL)가 문서형 DB(MongoDB)보다 근본적으로 적합하다. MongoDB를 선택하면 이미 확정된 관계형 도메인 모델을 문서형으로 다시 변환하는 불필요한 설계 비용이 발생하며, SC3가 요구하는 일관성을 애플리케이션 코드가 대신 떠안아야 한다.
2. PostgreSQL과 MySQL 모두 (a)(b)(d)에서 대등하지만, (c) 채팅 대량 누적 대응력에서 PostgreSQL의 선언적 파티셔닝이 PRD 8장이 명시한 확장성 리스크(채팅 이력 무기한 보존에 따른 선형 증가)에 더 직접적으로 대응한다.
3. 부가적으로, PostgreSQL의 범위 타입(`tsrange`)과 배제 제약(Exclusion Constraint, `EXCLUDE USING gist`)은 UC9/SC4(동일 팀원의 겹치는 시간대 일정 감지)를 구현할 때 애플리케이션 코드만으로 겹침을 판정하는 것보다 DB 수준에서 더 신뢰성 있게 지원할 수 있다. UC9는 현재 Should 항목이라 이번 결정의 필수 근거는 아니지만, 동일한 DB 선택이 후속 릴리즈에서도 재작업 없이 유효하다는 점에서 긍정적 요소로 반영한다.
4. 이 결정은 4-project-structure.md 1.3/2.2가 이미 명시한 "도메인 로직은 특정 DB의 구체적 API를 알지 못한다"는 원칙(리포지토리 인터페이스를 통한 DB 경계 분리) 위에서 내려진 것이므로, 향후 요구사항이 크게 달라지면(예: 채팅 데이터량이 관계형 스키마로 감당하기 어려운 규모가 되는 경우) 여전히 인프라 계층의 구현체만 교체하는 방식으로 재검토할 수 있다.

## 6. 주의사항 (범위 제한)

- 본 문서는 PRD/도메인 정의서에서 실제로 도출되는 요구사항에 한해서만 기술 요소를 다룬다. 캐시(Redis 등), 메시지 큐, CDN, 로드밸런서, 검색엔진 등은 PRD 어디에도 이를 요구하는 근거(트래픽 규모, 검색 요구사항 등)가 없으므로 이번 결정에 포함하지 않는다. 5-arch-diagram.md의 "참고" 절과 동일한 원칙을 유지한다.
- WebSocket 구현에 쓰일 구체 라이브러리(`ws` vs `socket.io`), ORM(Prisma vs TypeORM), 인증 방식(세션 vs JWT) 등은 이 문서의 범위를 벗어나는 세부 기술 설계 사항이며, 필요 시 별도 문서에서 다룬다.
- 본 문서의 DB 결정은 4-project-structure.md의 리포지토리 인터페이스 경계 원칙 위에서 내려졌으므로, 결정이 확정되었다고 해서 "DB를 특정 기술에 종속시켜도 된다"는 뜻은 아니다. 도메인/애플리케이션 계층이 PostgreSQL의 구체 API를 직접 알지 못하게 하는 경계는 계속 유지한다.
