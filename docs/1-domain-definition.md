## 1. 프로젝트 개요

**Team CalTalk**은 팀 단위로 일정을 관리하고, 캘린더와 채팅을 함께 사용하여 일정을 조율할 수 있는 팀 캘린더 + 채팅 통합 애플리케이션이다. 팀의 일정 정보를 한 곳에 모으고, 일정에 대한 논의(채팅)를 해당 일정에 귀속시켜 의사결정 맥락을 보존하는 것을 목표로 한다.

## 2. 문제 정의

- **P1. 일정 분산**: 팀원 각자의 개인 캘린더, 메신저, 엑셀 등에 일정이 흩어져 있어 일정 충돌 및 누락이 자주 발생한다.
- **P2. 맥락 단절**: 일정과 관련 대화(논의, 변경 사유 등)가 서로 다른 도구에 분리되어 있어, 특정 일정이 왜 그렇게 정해졌는지 의사결정 맥락을 다시 찾기 어렵다.
- **P3. 관리 어려움**: 팀장이 팀원 개인의 일정을 파악하거나 통제·관리하기 어려워 팀 전체 일정 운영에 비효율이 발생한다. (※ 여기서 "팀원 개인의 일정"은 팀에 속한 일정 중 해당 팀원이 참여자로 등록된 일정을 뜻하며, Out-of-scope의 "개인 일정"과는 다른 대상이다 — 10장 추적 매트릭스 참고)

## 3. 핵심 용어 정의 (도메인 용어집)

| 용어 | 정의 |
|---|---|
| **팀(Team)** | 함께 일정을 공유하는 사용자들의 집합. Team CalTalk의 모든 일정과 채팅은 팀을 단위로 존재한다. |
| **팀장** | 팀의 일정에 대해 읽기·쓰기 권한을 가지며, 팀원의 일정 변경 요청을 승인/거절할 수 있는 역할. |
| **팀원** | 팀의 일정에 대해 읽기 권한만을 가지며, 자신과 관련된 일정 변경이 필요할 때 채팅을 통해 변경 요청을 보낼 수 있는 역할. |
| **일정(Schedule/Event)** | 팀 캘린더 상에 등록되는 회의·이벤트 등의 항목. 필수 속성으로 제목, 시작일시, 종료일시, 참여자 목록을 가지며 월/주/일 단위 캘린더에 표시된다. (반복 일정 여부는 Out-of-scope) |
| **자신과 관련된 일정** | 특정 사용자가 참여자 목록에 등록되어 있는 일정. 팀원의 "일정 변경 요청" 권한은 이 범위로 한정된다. |
| **일정 충돌(Schedule Conflict)** | 동일 팀원이 참여자로 등록된 둘 이상의 일정이 서로 겹치는 시간대에 존재하는 상태. 시스템은 일정 생성/수정 시 충돌 여부를 감지하여 팀장에게 경고하되, 저장 자체를 자동으로 차단하지는 않는다. |
| **변경 요청(Change Request)** | 팀원이 자신과 관련된 일정의 수정을 원할 때 채팅을 통해 팀장에게 보내는 요청. 팀장의 승인이 있어야 실제 일정에 반영된다. |
| **채팅(대화)** | 특정 일정에 종속되어 이력이 남는 커뮤니케이션 수단. 일정 조율 및 변경 요청이 이루어지는 통로이다. |
| **권한(Permission)** | 사용자가 팀 일정에 대해 수행할 수 있는 동작의 범위(읽기/쓰기)를 정의하는 규칙. 역할(팀장/팀원)에 따라 다르게 부여된다(상세 규칙은 4장 참조). |
| **인증(Authentication)** | 사용자가 로그인을 통해 본인의 신원을 확인받는 절차. 인증되지 않은 사용자는 애플리케이션 기능을 사용할 수 없다. |

## 4. 핵심 액터 및 역할/권한

> 본 표는 팀 일정 및 관련 채팅에 대한 권한 규칙의 **단일 진실 공급원(SSOT)**이다. 이후 장에서는 권한 규칙을 다시 풀어쓰지 않고 "(4장 권한 규칙 참조)"로 표기한다.

| 액터 | 설명 | 일정 조회 | 일정 생성/수정/삭제(쓰기) | 변경 요청 발신 | 변경 요청 승인/거절 |
|---|---|---|---|---|---|
| **팀장** | 팀 일정을 직접 관리하는 책임자 | 가능 | 가능 (삭제 포함) | - | 가능 |
| **팀원** | 팀 일정을 조회하고 필요 시 변경을 요청하는 구성원 | 가능 | 불가 | 가능 (채팅으로, 자신과 관련된 일정에 한함) | - |

- 팀장과 팀원 모두 자신이 속한 팀의 일정 채팅에 메시지를 자유롭게 작성·열람할 수 있다(변경 요청 여부와 무관하게 조율용 대화 가능).
- 모든 액터는 **인증(로그인)**을 완료해야 위 기능을 사용할 수 있다.
- 한 사용자는 하나 이상의 팀에 속할 수 있으며, 팀별로 역할(팀장/팀원)이 부여된다.
- **불변조건**: 한 팀은 항상 정확히 1명의 팀장을 가진다(팀장이 0명이거나 2명 이상 동시에 존재하는 상태는 허용되지 않는다). 팀장 역할의 이전 규칙은 5장 "팀장 위임"을, 팀장 부재 상황의 처리는 5장 "팀 해체"를 참조한다.

## 5. 팀 라이프사이클

- **팀 생성**: 팀을 최초로 생성한 사용자는 자동으로 해당 팀의 팀장 역할을 부여받는다.
- **팀원 초대/가입**: 팀장은 다른 사용자를 팀원으로 초대할 수 있으며, 초대받은 사용자는 인증(로그인) 후 팀에 가입한다.
- **팀원 탈퇴**: 팀원은 소속 팀에서 탈퇴할 수 있으며, 탈퇴 시 해당 팀의 일정 조회 및 변경 요청 권한을 상실한다.
- **팀장 위임(영구 이전, 회수 불가)**: 팀장은 다른 팀원에게 팀장 역할을 위임할 수 있다. 위임은 일시적 대리가 아닌 영구적 역할 이전이며, 원 팀장이 위임을 취소하거나 역할을 회수하는 절차는 없다. 위임이 이루어지면 기존 팀장은 팀원으로 전환되고, 위임받은 팀원이 새 팀장이 된다. 팀은 항상 정확히 1명의 팀장만 가지며(4장 불변조건 참조), 위임 후 권한은 4장의 역할 정의를 따라 재부여된다.
- **팀 해체(팀 라이프사이클 종료)**: 유일한 팀장이 팀을 탈퇴하려는 경우, 반드시 사전에 다른 팀원에게 팀장 역할을 위임해야 한다. 위임할 팀원이 없는 경우(팀장 본인이 유일한 팀원인 경우) 팀은 해체되며, 해체 시 해당 팀의 모든 일정과 채팅 이력은 함께 삭제된다.

## 6. 핵심 도메인 개념 및 관계

- **팀**은 1명 이상의 **팀원**(팀장 포함)으로 구성된다(팀 생성 직후 및 팀 해체 직전에는 팀장 1명만 존재하는 상태도 정상 상태이다).
- **팀**은 여러 개의 **일정**을 가지며, 각 일정은 월/주/일 캘린더 뷰를 통해 팀원들에게 공유된다.
- 각 **일정**은 하나의 **채팅(대화) 이력**을 가지며, 해당 일정에 대한 논의와 변경 요청 내역이 여기에 기록된다.
- **팀원**은 자신과 관련된 **일정**에 대해 **변경 요청**을 생성할 수 있고, 변경 요청은 해당 일정의 채팅을 통해 **팀장**에게 전달된다.
- **팀장**은 변경 요청을 승인 또는 거절한다(권한 상세는 4장 권한 규칙 참조). 승인 시에만 실제 **일정** 정보가 갱신되며, 거절 시에는 사유와 함께 해당 일정의 채팅을 통해 팀원에게 통지되고 팀원은 재요청할 수 있다.
- **일정 삭제와 채팅 이력의 관계**: 팀장이 일정을 삭제하더라도 해당 일정에 종속되어 있던 채팅 이력은 삭제되지 않고 별도로 보존된다(SC2의 "채팅 이력 영구 보존" 원칙 참조). 단, 팀 해체 시에는 5장 "팀 해체" 규칙에 따라 해당 팀에 속한 모든 일정과 채팅 이력이 함께 삭제된다.
- 개념 관계 요약:
  - 팀 1 : N 일정
  - 일정 1 : 1 채팅(이력)
  - 일정 1 : N 변경 요청
  - 사용자 1 : N 팀 소속(역할 포함)

## 7. 핵심 기능(유스케이스) 요약

| ID | 유스케이스 | 설명 |
|---|---|---|
| UC1 | 로그인/인증 | 사용자는 인증 후에만 서비스 기능을 이용할 수 있다. |
| UC2 | 팀 일정 조회 | 팀원/팀장은 월/주/일 단위로 팀 일정을 조회한다. |
| UC3 | 팀 일정 등록/수정/삭제(팀장) | 팀장은 팀 일정을 생성, 수정, 삭제할 수 있다(4장 권한 규칙 참조). |
| UC4 | 일정 공유 | 등록된 일정은 팀 내 모든 팀원(팀장 포함)에게 공유되어 조회 가능하다. |
| UC5 | 캘린더-채팅 연동 조율 | 사용자는 캘린더와 해당 일정의 채팅창을 함께 보면서 일정을 조율한다. |
| UC6 | 일정 변경 요청(팀원) | 팀원은 자신과 관련된 일정에 대해 채팅으로 변경을 요청한다. |
| UC7 | 변경 요청 승인/거절(팀장) | 팀장은 팀원의 변경 요청을 검토하여 승인 또는 거절하며, 승인 시 일정에 반영한다. 거절 시에는 사유와 함께 팀원에게 채팅으로 통지하고, 팀원은 재요청할 수 있다. |
| UC8 | 일정별 채팅 이력 확인 | 사용자는 일정 단위로 남아있는 채팅 이력을 통해 논의 맥락을 확인한다. |
| UC9 | 일정 충돌 감지/경고 | 팀장이 일정을 생성/수정할 때, 시스템은 동일 팀원이 참여하는 다른 일정과 시간이 겹치는지(일정 충돌) 확인하여 경고를 표시한다. 경고는 참고 정보이며 저장 자체를 자동으로 차단하지는 않는다(In-scope). |

## 8. 범위 (Scope)

### In-scope
- 팀 단위 월/주/일 캘린더를 통한 일정 관리 및 공유
- 일정 단위로 종속되는 채팅 및 그 이력 관리
- 팀장/팀원의 역할 기반 권한 구분(4장 권한 규칙 참조)
- 팀원의 채팅 기반 일정 변경 요청 및 팀장의 승인/거절 워크플로우(거절 시 사유 통지 및 재요청 포함)
- 팀 생성, 팀원 초대/가입/탈퇴, 팀장 위임 등 팀 라이프사이클(5장 참조)
- 일정 충돌 감지 및 경고(UC9)
- 로그인 기반 사용자 인증

### Out-of-scope
- 개인(비팀) 일정 관리 — 팀에 속하지 않는 사용자의 사적 캘린더 관리를 의미하며, P3에서 다루는 "팀에 속한 일정에 대한 팀장의 통제력 부족" 문제와는 별개의 대상이다.
- 외부 캘린더(Google/Outlook 등) 연동
- 이메일/푸시 등 앱 외부 알림 채널
- 결제, 구독 등 과금 관련 기능
- 화상회의, 파일 공유 등 채팅 외 부가 협업 기능
- 팀 간 일정 공유 또는 조직 전체 통합 일정 뷰
- 반복 일정(recurring event) 관리

## 9. 성공 기준 및 제약사항

**성공 기준**

| ID | 성공 기준 | 검증 방법 (Given-When-Then) |
|---|---|---|
| SC1 | 해당 팀의 모든 일정이(기간 제한 없이) 팀 캘린더 한 곳에서 조회 가능해야 한다. | Given 팀에 과거/현재/미래 일정이 등록되어 있을 때, When 팀원 또는 팀장이 팀 캘린더를 조회하면, Then 기간 제한 없이 해당 팀의 모든 일정이 캘린더에 표시된다. |
| SC2 | 일정과 관련된 채팅 이력은 영구 보존되며 유실되지 않아야 한다. 단, 팀 해체 시에는 6장 규정에 따라 해당 팀의 모든 일정 및 채팅 이력이 예외적으로 함께 삭제된다. | Given 일정에 채팅 메시지가 기록되었을 때, When 이후 시점에 해당 일정을 다시 조회하면, Then 모든 메시지가 순서대로 유실 없이 표시된다. 단, Given 해당 일정이 속한 팀이 해체된 경우에는, When 이후 시점에 조회를 시도하면, Then 6장 규정에 따라 해당 팀의 모든 일정 및 채팅 이력이 함께 삭제되어 조회되지 않는다. |
| SC3 | 팀원의 일정 변경 요청은 팀장의 승인 없이 일정에 반영되지 않아야 한다(권한 무결성 보장, 4장 권한 규칙 참조). | Given 팀원이 변경 요청을 보냈을 때, When 팀장이 아직 승인하지 않았다면, Then 원래 일정 정보는 변경되지 않은 채로 유지된다. |
| SC4 | 겹치는 시간대에 동일 팀원이 참여하는 다른 일정이 이미 존재할 경우, 일정 저장(생성/수정) 시점에 경고가 표시되어야 한다(UC9). | Given 팀원 A가 참여자로 등록된 일정이 이미 존재하는 상태에서, When 팀장이 팀원 A가 참여자로 등록되고 시간대가 겹치는 일정을 생성 또는 수정하여 저장하면, Then 저장 시점에 일정 충돌 경고가 표시된다(저장 자체는 차단되지 않는다). |

**제약사항**

- 모든 기능은 인증된 사용자만 접근 가능해야 한다.
- 일정에 대한 쓰기 권한 규칙은 4장 권한 표를 따른다(4장 권한 규칙 참조).
- **동시 편집 충돌 처리**: 팀 일정에 대한 쓰기 권한은 팀장 1인에게만 부여되며, 한 팀은 항상 정확히 1명의 팀장만 가지므로(4장 불변조건 참조), 복수 사용자가 동일 일정을 동시에 쓰기 편집하는 상황은 현재 권한 모델상 구조적으로 발생하지 않는다. 별도의 동시 편집 잠금/병합 로직은 필요하지 않다.
- **채팅 이력 보존 기간**: 채팅 이력은 기간 제한 없이 영구 보존한다(팀 해체 시 예외 삭제는 5장·SC2 참조).

## 10. 추적 매트릭스

| 문제 ID | 문제 | 관련 유스케이스 | 관련 성공 기준 |
|---|---|---|---|
| P1 | 일정 분산 | UC2, UC4 | SC1 |
| P2 | 맥락 단절 | UC5, UC8 | SC2 |
| P3 | 관리 어려움(팀장의 팀 일정 통제 어려움) | UC3, UC6, UC7, UC9 | SC3, SC4 |

※ P3는 "팀에 속한 일정"에 대한 팀장의 통제력 부족 문제이며, Out-of-scope의 "개인 일정"(팀에 속하지 않는 사용자의 사적 캘린더)과는 서로 다른 대상이다. P3는 팀장 쓰기 독점 + 팀원 변경요청 승인제라는 권한 모델(4장, UC3/UC6/UC7)과 일정 충돌 감지 및 경고(UC9, SC4)로 해결된다.

※ UC1(로그인/인증)은 이 표의 어느 문제 행에도 매핑하지 않는다. 4장의 "모든 액터는 인증을 완료해야 한다" 규칙에 따라 UC1은 P1~P3 모든 문제 해결의 전제조건이 되는 횡단 관심사(cross-cutting concern)이기 때문이다.
